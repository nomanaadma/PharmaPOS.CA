

# Clean Architecture — Dependency Rule Analysis

## The Dependency Rule

In Clean Architecture, dependencies must **only point inward**. The allowed reference graph is:

```mermaid
graph LR
    Razor["🖥️ Razor (Presentation)"] --> Application
    Razor --> Contracts
    Razor --> Infrastructure
    Infrastructure --> Application
    Infrastructure --> Domain
    Application --> Domain
    Application --> Contracts
    Contracts --> Domain
```

> [!IMPORTANT]
> The key rule: **outer layers depend on inner layers, never the reverse.**

---

## ⚠️ Violation 1 — Razor → Domain (direct reference)

**The issue:** [PharmaPOS.Razor.csproj](file:///d:/.Net%20Works/PharmaPOS/PharmaPOS.Razor/PharmaPOS.Razor.csproj#L21) has a direct `<ProjectReference>` to `PharmaPOS.Domain`. This means Razor pages and mappers use Domain entities directly instead of going through Contracts/DTOs.

**28+ files** in Razor use `PharmaPOS.Domain.*` namespaces — mappers, view models, Razor pages, etc.

**Why it's a problem:**
- Presentation knows about internal domain structure (aggregate roots, value objects, entity details)
- If you refactor a Domain entity, the UI layer breaks
- The Razor layer should only speak "DTO language" defined in Contracts

**The fix:** Razor should reference **only** Application, Contracts, and Infrastructure (for DI wiring). All Domain entities returned from Application services should be mapped to response DTOs in Contracts, and Razor should only consume those DTOs.

---

## ⚠️ Violation 2 — Contracts → Domain (reference)

**The issue:** [PharmaPOS.Contracts.csproj](file:///d:/.Net%20Works/PharmaPOS/PharmaPOS.Contracts/PharmaPOS.Contracts.csproj#L10) references `PharmaPOS.Domain`, and many response DTOs directly embed Domain entities:

- [`BillEditResponse`](file:///d:/.Net%20Works/PharmaPOS/PharmaPOS.Contracts/Responses/BillEditResponse.cs) — contains `Bill` and `Dictionary<int, List<Batch>>`
- [`BillDetailsResponse`](file:///d:/.Net%20Works/PharmaPOS/PharmaPOS.Contracts/Responses/BillDetailsResponse.cs) — contains `Bill` and `Dictionary<int, Batch>`
- [`PurchaseDetailsResponse`](file:///d:/.Net%20Works/PharmaPOS/PharmaPOS.Contracts/Responses/PurchaseDetailsResponse.cs) — contains `Purchase`, `Batch`, `Supplier`
- [`MedicineStockSummaryResponse`](file:///d:/.Net%20Works/PharmaPOS/PharmaPOS.Contracts/Responses/MedicineStockSummaryResponse.cs) — contains `IEnumerable<Batch>`
- [`InventoryReportResponse`](file:///d:/.Net%20Works/PharmaPOS/PharmaPOS.Contracts/Responses/InventoryReportResponse.cs) — contains `Medicine`
- Request DTOs use `PharmaPOS.Domain.Common.Enums` (Gender, Status, DiscountType)

**Why it's a problem:**
- Contracts is supposed to be the "API surface" — pure DTOs with no internal knowledge
- Embedding `Bill`, `Batch`, `Purchase` etc. means Contracts is not a true abstraction boundary
- If Domain changes, Contracts and all consumers break

**Two approaches to fix:**

### Option A: Mirror enums in Contracts (strict separation)
- Copy `Gender`, `Status`, `DiscountType` into `PharmaPOS.Contracts.Enums`
- Replace all Domain entity references in responses with flat DTO properties
- Remove the Domain reference from Contracts entirely

### Option B: Allow Contracts → Domain for shared enums only (pragmatic)
- Keep the Domain reference **only** for `PharmaPOS.Domain.Common.Enums`
- Replace all entity-level references (`Bill`, `Batch`, `Purchase`, etc.) with flat DTOs
- This is a common pragmatic compromise in many projects

---

## ✅ Infrastructure → Domain (NOT a violation)

**This is perfectly fine.** Infrastructure implements the repository interfaces defined in Application, and those interfaces work with Domain entities. Infrastructure *must* reference Domain to:
- Configure EF Core entity mappings (`IEntityTypeConfiguration<T>`)
- Map database rows to Domain entities in repository implementations
- Access `DbSet<DomainEntity>`

This follows the Clean Architecture dependency rule: Infrastructure (outer ring) → Domain (innermost ring) points inward.

# Remove Domain References from Contracts & Razor

Eliminate all `PharmaPOS.Domain` references from both `PharmaPOS.Contracts` and `PharmaPOS.Razor` to achieve strict Clean Architecture separation.

## Proposed Changes

### Phase 1 — Mirror Enums into Contracts

Create `PharmaPOS.Contracts/Enums/` with copies of the Domain enums. These will be the **only** enum types used by Contracts, Razor, and request/response DTOs.

#### [NEW] `PharmaPOS.Contracts/Enums/Status.cs`
Mirror of `PharmaPOS.Domain.Common.Enums.Status` (Active/InActive).

#### [NEW] `PharmaPOS.Contracts/Enums/Gender.cs`
Mirror of `PharmaPOS.Domain.CustomerAggregate.Gender` (NotSpecified/Male/Female).

#### [NEW] `PharmaPOS.Contracts/Enums/DiscountType.cs`
Mirror of `PharmaPOS.Domain.Common.Enums.DiscountType` (Percentage/Flat).

---

### Phase 2 — Flatten Contracts Response DTOs

Replace every Domain entity reference in response/request DTOs with flat primitive properties. Each existing DTO that embeds a Domain entity (e.g. `Bill`, `Batch`, `Purchase`, `Medicine`, `Supplier`, `Media`, `Setting`) gets rewritten as a flat record.

#### [MODIFY] `PharmaPOS.Contracts/Responses/BillDetailsResponse.cs`
- **Before:** `Bill Bill, Dictionary<int, Batch> BatchesById, ...`
- **After:** Flat DTO with `int Id, string Name, string? Email, ...` + `List<BillItemDto> Items` + `string PaymentMethodName`

#### [NEW] `PharmaPOS.Contracts/Responses/BillItemDto.cs`
Flat DTO: `MedicineName, BatchName, Expiry, Qty, SalePrice, Gross, DiscountValue, TaxPrice, Price`

#### [MODIFY] `PharmaPOS.Contracts/Responses/BillEditResponse.cs`
- **Before:** `Bill Bill, Dictionary<int, List<Batch>> BatchesByMedicine, ...`
- **After:** Flat DTO with bill fields + `List<BillEditItemDto> Items`

#### [NEW] `PharmaPOS.Contracts/Responses/BillEditItemDto.cs`
Flat DTO for edit items including `List<BatchOptionDto> Batches`

#### [NEW] `PharmaPOS.Contracts/Responses/BatchOptionDto.cs`
Flat DTO: `Id, Batch, Qty, Sold`

#### [MODIFY] `PharmaPOS.Contracts/Responses/PurchaseDetailsResponse.cs`
- **Before:** `Purchase Purchase, List<Batch> Batches, ..., Supplier Supplier`
- **After:** Flat DTO with purchase fields + supplier fields + `List<PurchaseBatchDto> Batches`

#### [NEW] `PharmaPOS.Contracts/Responses/PurchaseBatchDto.cs`

#### [MODIFY] `PharmaPOS.Contracts/Responses/InventoryReportResponse.cs`

### Phase 3 — Add Contracts Enums to Domain (Mapping Layer)

The Application and Infrastructure layers need to map between `Contracts.Enums.X` ↔ `Domain.X` enums. Since the enum values are identical (same names, same integer values), we can cast directly: `(Domain.Common.Enums.Status)(int)contractsStatus`.

#### [NEW] `PharmaPOS.Application/Mappers/EnumMapper.cs`
Static helper with `ToDomain()` and `ToContracts()` methods for each enum pair.
